## Мотивация

### Критические бизнес-проблемы

Компания сталкивается с серьезными проблемами, которые напрямую влияют на прибыльность. 

Потеря заказов без видимости причин приводит к тому, что клиенты жалуются на несвоевременную доставку заказов — месяцы вместо обещанных трех недель. 

После открытия API для B2B партнеров количество жалоб возросло настолько, что компания уже потеряла несколько крупных контрактов.

Операторы сталкиваются с медленной работой MES дашборда, тратя время на ожидание загрузки вместо продуктивной работы с заказами. 

Долгий расчет стоимости, занимающий от 2 до 30 минут, существенно ухудшает пользовательский опыт. Отсутствие SLA контроля означает, что у компании нет инструментов для отслеживания выполнения обещаний клиентам.

### Экономическое обоснование

Затраты на внедрение мониторинга, включая инфраструктуру и время разработки меньше, чем потяря прибыли от контрактов. 

А так же увеличит эффективности операторов, что даст экономию на дистаниции.

## Выбор подхода к мониторингу

### RED (Rate, Errors, Duration) для API сервисов

Подход RED применяется к Shop API, MES API и CRM API, поскольку эти пользовательские сервисы требуют мониторинга качества сервиса.

Rate помогает понять нагрузку от разных источников (B2C vs B2B), Errors показывают проблемы интеграции между системами, а Duration критично для пользовательского опыта, особенно для MES дашборда.

### USE (Utilization, Saturation, Errors) для инфраструктуры

USE применяется к PostgreSQL базам данных и серверным инстансам, поскольку эти ресурсы требуют мониторинга использования и насыщенности. 

PostgreSQL базы являются узким местом производительности, единственные инстансы сервисов создают риски, и критично знать приближение к пределам ресурсов.

### Four Golden Signals для критических компонентов

Этот подход применяется к RabbitMQ, бизнес-процессам обработки заказов и S3 storage. RabbitMQ является сердцем интеграции между системами, бизнес-процессы требуют комплексного мониторинга, а баланс между техническими и бизнес-метриками обе

## Выбор метрик

### Критические технические метрики

#### Number of requests (RPS)

Number of requests (RPS) для всех API показывает нагрузку и тренды роста, что критично для планирования масштабирования. 

Метрика содержит ярлыки api_name, endpoint, http_method, user_type с порогами: Shop API > 100 RPS, MES API > 50 RPS, CRM API > 30 RPS.

#### Response time (latency)
Response time (latency) для всех API является ключевой метрикой, поскольку медленная загрузка MES дашборда — основная проблема компании. Ярлыки включают api_name, endpoint, operation_type с порогами MES API > 2s (P95), Shop API > 1s (P95).

#### Number of HTTP 500
Number of HTTP 500 для всех API критично отслеживать, поскольку ошибки приводят к потере заказов и жалобам клиентов. Метрика использует ярлыки api_name, endpoint, error_type с порогом > 1% error rate.

### Метрики инфраструктуры

#### CPU % для MES API
CPU % для MES API важна, поскольку MES API выполняет тяжелые расчеты стоимости продолжительностью до 30 минут. Метрика с ярлыком instance_id имеет порог > 80%.

#### Memory Utilisation
Memory Utilisation для баз данных критична для PostgreSQL баз с ростом данных в единственных инстансах. Ярлыки instance_id, db_name с порогом > 85%.

#### Number of connections
Number of connections для баз данных отслеживает ограничения PostgreSQL, которые могут блокировать новые заказы. Ярлыки instance_id, connection_type с порогом > 80% от max_connections.
Метрики RabbitMQ

#### Number of dead-letter-exchange
Number of dead-letter-exchange messages — критически важная метрика, поскольку потерянные сообщения равны потерянным заказам, что является основной бизнес-проблемой. Ярлыки queue_name, message_type с порогом > 0 messages (критично).

#### Number of messages in flight
Number of messages in flight показывает накопление необработанных заказов с ярлыками queue_name, priority и порогом > 1000 messages.
Дополнительные бизнес-метрики

#### Order processing time by status
Order processing time by status решает основную проблему — заказы выполняются месяцами вместо 3 недель. Ярлыки order_status, order_type, complexity с порогом > 21 days total.

#### Price calculation duration
Price calculation duration отслеживает расчеты, занимающие 2-30 минут и блокирующие пользователей. Ярлыки model_complexity, user_type с порогом > 5 minutes.

#### Failed order rate
Failed order rate критична, поскольку потеря заказов приводит к потере контрактов. Ярлыки failure_reason, order_source с порогом > 2%.


## План действий

Реализация разделена на четыре фазы общей продолжительностью 6-9 недель. 

### Фаза 1 (1-2 недели)
Фаза 1 (1-2 недели) включает развертывание инфраструктуры мониторинга: Prometheus как time-series базы данных, Grafana для визуализации, Alertmanager для уведомлений и создание каналов для алертов.

### Фаза 2 (2-3 недели)
Фаза 2 (2-3 недели) посвящена инструментированию приложений: добавление Micrometer для Spring Boot приложений, интеграция .NET metrics для MES API, настройка RabbitMQ Prometheus plugin и добавление PostgreSQL Exporter.

### Фаза 3 (1-2 недели)
Фаза 3 (1-2 недели) фокусируется на бизнес-метриках: создание custom metrics для отслеживания времени обработки заказов, метрик длительности расчета стоимости и трекинга статусов заказов.

### Фаза 4 (1-2 недели)
Фаза 4 (1-2 недели) завершает внедрение созданием дашбордов и настройкой алертов: Executive Dashboard для руководства, Technical Dashboard для DevOps команды, Operations Dashboard для операторов и внедрением PagerDuty для критических алертов.

## Техническая архитектура

Архитектура мониторинга включает Prometheus (2 инстанса с HA) как центральную time-series БД, Grafana (2 инстанса за load balancer) для визуализации и AlertManager (3 инстанса в кластере) для управления алертами.

Сбор данных организован по pull-модели Prometheus каждые 15 секунд через /metrics endpoints приложений и специализированные exporters для инфраструктуры. Система алертинга включает 3 уровня серьезности с эскалацией от Telegram до PagerDuty и автоматическим созданием инцидентов в JIRA.
